## 1. 배경 및 문제정의

개인투자자는 두 갈래의 정보 비대칭에 노출돼 있다: (1) 커뮤니티에 도는 테마주 루머가 실제 공시로
뒷받침되는지 모르고, (2) 실제 공시를 읽어도 상투적 IR 화법이 무엇을 의미하는지 모른다. 두 문제
모두 근본적으로 "**공시 텍스트 하나를 놓고, 그 뒤에 뭐가 있(었)는지 찾아준다**"는 동일한 과제이며,
대상 범위만 다르다 — 전자는 **특정 회사**의 공시가 **특정 주장**을 뒷받침하는지(개별 사실 대조),
후자는 **표현 패턴 전체**를 놓고 과거 통계적으로 무엇을 의미했는지(집계 통계)를 다룬다.

## 2. 왜 통합하는가

루머를 팩트체크하는 과정에서 실제 공시 원문을 가져오게 되는데, 그 원문 안에 상투적 IR 화법이
섞여 있으면 그 자리에서 곧바로 화법 통계를 함께 보여줄 수 있다. 즉 공시 국어사전 기능은 별도
화면이 아니라 **팩트체크 결과 카드 안의 자동 주석**으로 결합된다(문구만 따로 검색하는 단독
진입점도 유지한다). 이렇게 합치면:

- 데이터 파이프라인(DART 수집·정규화)을 완전히 공유한다
- 평가용 gold set 작업(과거 공시 사례 라벨링)을 하나로 합칠 수 있다 — 팩트체크 gold set과 화법
  클러스터-사후이벤트 라벨링이 같은 "과거 공시 사례 수집·라벨링" 작업에서 파생되기 때문
- 데모 시나리오가 하나로 통일된다: "루머 하나 넣었더니 팩트체크 + 화법 해설까지 한 번에 나온다"

## 3. 타겟 사용자

- 커뮤니티/유튜브에서 테마주 루머를 접한 개인투자자
- 공시·IR 자료를 읽지만 상투 화법의 함의를 모르는 개인투자자
- (공통) "5분 안에 1차 검증"을 원하는 사람 — 전문 애널리스트가 아닌 일반 개인투자자

## 4. 핵심 기능

1. **입력창 하나** — 루머 문장이든 공시 문장이든 아무거나 붙여넣는다
2. 시스템이 입력을 분류: 특정 종목에 대한 주장(claim)인지, 일반적 화법 문구인지 판단
3. **L2a 팩트체크**: 종목이 특정되면 DART 전문검색으로 해당 종목 공시와 대조 → 사실 나열
   (긍정/부정 동일 비중, 등급·신호등 없음)
4. **L2b 화법통계 주석**: 팩트체크 결과에 포함된 공시 원문에 알려진 상투구 패턴이 있으면 자동으로
   "이 표현, 과거 N건 중 M건이 X로 이어짐" 통계를 카드에 주석으로 첨부. 문구만 단독 검색하는
   진입점도 별도 제공
5. 근거 공시 원문 링크 첨부 — 최종 판단은 항상 사용자 몫

## 5. 데이터 & 파이프라인 (공통)

- **DART OpenAPI**(원문 zip/XML, 재무정보 API) — 무료·즉시 발급 확인됨(2026-09-09 리서치)
- KIND(자율공시), 공매도·지분공시
- 공시 원문 → 서식 유형별 섹션 청킹(MOU/유상증자/최대주주변경 등 표준 항목 구조 활용) → 임베딩
  → 종목코드/공시일자/서식유형 메타와 결합한 하이브리드 검색 + 상투구 클러스터 벡터 인덱스

## 6. 아키텍처 (레이어)

| 레이어 | 내용 |
| --- | --- |
| L0 수집 | DART 원문·재무정보 API 수집·정규화 — 공통 |
| L1 검색 | 종목별 공시 이력 검색(키워드+임베딩) + 화법 클러스터 벡터 인덱스 — 공통 |
| L2a 팩트체크 엔진 | 루머 클레임 vs 실제 공시 사실 대조. narrative_qa `qa/chain.py` guard(groundedness) 패턴 재사용 |
| L2b 화법통계 엔진 | 문구 → 클러스터 매칭 → 사후 이벤트 통계. L2a 출력에 자동 주석으로 결합 |
| L3 통합 리포트 | "사실 대조 결과 + (매칭 시) 이 표현의 과거 패턴"을 한 장의 카드로 조립 |
| L4 UI | 입력창 하나 — 시스템이 팩트체크/화법통계 중 맞는 것을 자동 적용 |
| L5 평가 | 팩트체크 gold set + 화법 클러스터 라벨링 — 같은 "과거 공시 사례 라벨링" 작업에서 공동 파생 |

## 7. 규제 리스크 및 대응

두 기능 공통 방어선: **"개별 종목 매수/매도 판단"을 만들지 않고, "공시에 실제로 뭐라고 쓰여
있는가 / 과거 패턴이 통계적으로 어땠는가"까지만 출력**한다.

- 매수/매도 추천, 목표가, 수익률 예측 일절 금지
- 신빙성 신호등·종합 등급 등 종합 판단 지표 배제, 개별 사실·통계 나열까지만
- 부정적 사실만 골라 나열하지 않도록 긍정/부정 사실 동일 비중 노출을 UI 레벨에서 강제
- 화법통계에서 개별 종목명 노출은 최소화(집계 통계 우선), 표본 부족 클러스터는 유의성 미달 명시

이 방어선은 이전 세션에서 반복 확인된 자본시장법상 유사투자자문업 리스크 패턴(불특정 다수 대상
특정 금융투자상품 투자판단 자문)을 피하기 위한 것이며, **실제 서비스화 이전에는 법률 자문을
통한 최종 검증이 필요**하다 — 이 문서는 과제 범위의 1차 판단이다.

## 8. 경쟁 서비스 비교 (2026-09-09 WebSearch/WebFetch 기준)

- **공시줍줍**(비즈워치 뉴스레터): 기자가 매일 수작업으로 공시를 선별·해설하는 편집형 서비스.
  자동화된 셀프서비스 도구가 아니라는 점에서 차별화됨
- **한경 유레카**: "공시 분석으로 투자할 가치가 있는 종목 발굴" — 방향이 반대(종목 발굴 vs
  검증/해설)라 성격이 다름
- "루머 입력 → 팩트체크" 또는 "문장 입력 → 화법 통계"를 자동화된 셀프서비스로 제공하는 직접
  경쟁 서비스는 특정하지 못함(존재하지 않는다는 증명은 아니므로 착수 전 재검증 권장)

## 9. 평가 방법

- 팩트체크: 과거 실제 테마주 루머 사례 20~30건 gold set → 팩트체크 결과와 실제 사후 공시 일치
  여부(정밀도·재현율)
- 화법통계: 라벨링된 클러스터-통계의 표본 수·통계적 유의성 + 새 문장의 클러스터 매칭 정확도(사람
  검수)
- 두 평가 모두 같은 "과거 공시 사례 라벨링" gold 작업에서 파생되므로 하나의 라벨링 스프린트로
  동시 진행 가능

## 10. 리스크와 완화

| 리스크 | 완화 |
| --- | --- |
| 부정적 사실 나열이 암묵적 매도 시그널로 읽힘 | 긍정/부정 사실 동일 비중 노출 강제 |
| 개별 종목명 노출로 화법통계가 암묵적 종목 판단처럼 읽힘 | 집계 통계 우선, 종목명은 클릭 시에만 |
| 루머 원문 키워드 추출 실패(비정형 텍스트) | LLM 추출 + 실패 시 재입력 요청 |
| DART 검색 커버리지 누락(비상장 등) | 코스피·코스닥 상장사로 스코프 한정 |
| 표본 부족 클러스터의 통계 왜곡 | 최소 표본 수 미달 시 유의성 미달 명시 |
| 규제 판단의 최종 확실성 부족 | 실제 서비스화 전 법률 자문 필요함을 문서에 명시(본 문서 8절) |

## 11. 팀 3인 분담

| 파트 | 담당 | 범위 |
| --- | --- | --- |
| A. 데이터/라벨링 | **이승노 (powercodingman)** | DART 공통 파이프라인 + 과거 공시 사례 라벨링(팩트체크 gold + 화법 클러스터-사후이벤트, 하나의 작업으로 통합) |
| B. L2a 팩트체크 엔진 | **김가빈 (9abin)** | 클레임 vs 사실 대조 로직, groundedness guard |
| C. L2b 화법통계 엔진 + L3/L4 통합 UI | **우지훈 (jh3779)** | 클러스터 매칭 검색 + 결과 카드 조립 + 데모 화면 |

> 통합 UI(L3/L4)는 고유 로직이 없는 접착 계층이라 담당이 유동적이다. C가 맡는 이유는 어차피 L2b
> 결과를 L2a 출력에 주석으로 합치는 조립 작업을 해야 해서일 뿐, B가 맡아도 무방하다. 다만 B·C는
> 착수 전 **L2a/L2b 출력 스키마(인터페이스 계약)**를 먼저 합의해야 한다 — 안 정해두면 UI 작업이
> 두 엔진의 완성을 기다리는 병목이 생긴다.

## 12. Phase 및 마일스톤

### Phase 1 — 기반 구축 (공통)

- **A(이승노)** 주도: DART API 키 발급, 원문 수집·정규화, 서식별 청킹, 종목코드 인덱싱
- **B(김가빈)·C(우지훈)**: L2a/L2b 출력 스키마 합의 — 이후 병렬 작업의 전제 조건
- **완료 기준**: 종목 하나 기준 최근 공시 검색 가능, 출력 스키마 문서화 완료

### Phase 2 — 핵심 엔진 병렬 개발

- **A**: Phase 1 완료 즉시 상투구 클러스터링 + 사후 이벤트 라벨링 착수(전체 일정 중 가장 오래
  걸리는 작업이라 최대한 앞당겨 시작)
- **B**: L2a claim verification 엔진 구현 + 과거 루머 사례 20~30건 gold set 수집·검수
- **C**: L2b 클러스터 매칭 검색 로직 skeleton + 데모 UI 와이어프레임(입력창 + 결과 카드 레이아웃)
- **완료 기준**: 각자 엔진 단위 테스트 통과, gold set 20건 이상·클러스터 라벨 20개 이상 확보

### Phase 3 — 통합

- **C** 주도: L2a·L2b 산출물을 L3 통합 리포트 카드로 조립, L4 데모 화면 완성
- **A·B**: 통합 과정에서 나오는 데이터/로직 버그 픽스 지원
- **완료 기준**: 엔드투엔드 데모 동작 — 루머 입력 → 팩트체크 + (해당 시) 화법 통계 카드 출력

### Phase 4 — 평가 및 마무리

- 전원: 평가 지표 측정(정밀도·재현율, 클러스터 유의성), 규제 방어선 최종 재점검, 발표자료 정리
- **완료 기준**: 평가 결과표 완성, 팀 리뷰 통과, (필요 시) 강사 배포 양식 정식 기획서로 재작성

## 13. 성공 지표 (초안)

- 팩트체크: gold set 대비 정밀도·재현율 각 80% 이상
- 화법통계: 표본 20건 이상인 클러스터 15개 이상 확보
- 데모: 루머 입력 → 결과 카드 출력까지 응답시간 10초 이내(발표 데모 기준)

> 정확한 일정(기획서 마감일·중간발표일·최종발표일)은 아직 미확정 — 확인되는 대로 Phase별 기한을
> 채워 넣는다.

## 14. 기존 프로젝트(narrative_qa)와의 관계

이 제안이 채택되면 현재 `main`의 미스터리 추론 캘리브레이션 게임(`narrative_qa/`) 프로젝트를
대체하게 된다. narrative_qa는 팀원(powercodingman/9abin)이 이미 상당 부분 구현한 코드베이스이므로,
**이 문서는 결정이 아니라 제안이며, 채택 여부는 팀 전원 리뷰·논의 후 확정한다.**
