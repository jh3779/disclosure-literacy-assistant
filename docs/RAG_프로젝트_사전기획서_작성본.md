## 1. 프로젝트 개요

### 1.1 프로젝트명

**프로젝트명**
공시 리터러시 어시스턴트

**한 줄 설명**
커뮤니티에 도는 테마주 루머를 DART 공시로 사실 대조하고, 상투적 IR 화법이 과거 통계적으로
무엇을 의미했는지 보여주는 도구. 매수/매도 추천·목표가·등급은 제공하지 않는다.

### 1.2 프로젝트 배경

| 항목 | 작성 내용 |
| --- | --- |
| 현재 업무/서비스 환경 | 개인투자자는 커뮤니티·유튜브·오픈채팅에서 접한 테마주 루머와, 공시·IR 자료의 상투적 화법을 스스로 해석해야 하는 환경에 있다. |
| 기존 방식 | 루머는 DART 전자공시시스템에서 직접 검색해 확인해야 하고, 화법의 함의는 경험이나 "공시줍줍" 같은 뉴스레터의 사후 해설에 의존한다. |
| 기존 방식의 문제점 | DART 전문검색 UI가 불친절하고 공시서식 구조(MOU/유상증자/최대주주변경 등)를 모르면 무엇을 봐야 할지 판단하기 어렵다. 화법 해설은 기자가 매일 수작업으로 골라 쓰는 편집형이라 즉시성·자동화가 없다. |
| 문제로 인해 발생하는 비용·시간·불편 | 검증 없이 루머가 확산되고, 손실을 본 뒤에야 "미리 확인했어야 했다"는 사후 공유가 반복된다. 화법의 함의를 몰라 공시를 읽어도 실질적 의미를 놓친다. |
| 지금 이 문제를 해결해야 하는 이유 | 테마 유행마다 개인투자자 피해가 반복되고, 공개된 1차 데이터(DART, 무료·즉시 발급 확인됨)가 있음에도 이를 몇 분 안에 대조·해석해주는 셀프서비스 도구가 없다. |

## 5. 문제 해결 전략

### 5.1 어떻게 문제를 해결할 것인가?

| 항목 | 작성 내용 |
| --- | --- |
| 개선하려는 사용자 불편 | 루머 검증·화법 해석에 드는 시간과 전문성 장벽 |

| 사용자에게 제공할 최종 경험 | 입력창 하나에 루머나 공시 문장을 넣으면, 사실 나열 + (해당 시) 화법 통계가 담긴 리포트 카드를 받는 경험 |

위해 [DART 공시 원문·재무정보]를 활용하여 [클레임 검증(RAG 기반 사실 대조) + 상투구
클러스터 통계 검색] 방식으로 필요한 정보를 제공한다.

### 5.3 기존 방식과 개선 방식 비교

| 구분 | 기존 방식 | 개선 방식 |
| --- | --- | --- |
| 질문 방식 | DART 전문검색 화면에서 직접 조건 입력 | 루머·공시 문장을 자연어 그대로 입력 |
| 정보 탐색 | 서식 구조를 알아야 어디를 봐야 할지 판단 가능 | 시스템이 자동으로 종목·키워드를 추출해 검색 |
| 답변 작성 | 없음(원문을 그대로 읽어야 함) | 사실 나열 + 화법 통계를 카드 형태로 정리 |
| 출처 확인 | 원문을 직접 대조 | 근거 공시 원문 링크를 자동 첨부 |
| 최신 정보 | 수동 재검색 필요 | 최신 공시를 배치로 반영(주기는 Phase 2에서 결정) |

## 6. 왜 RAG를 사용하는가?

### 6.1 일반 LLM만으로 해결하기 어려운 이유

| 항목 | 작성 내용 |
| --- | --- |
| 사내 또는 서비스 고유 데이터가 필요한가? | 예 — DART 공시 원문은 LLM 사전학습 시점 이후의 최신·세부 정보를 담고 있다 |
| 최신 정보가 필요한가? | 예 — 공시는 매 영업일 갱신된다 |
| 답변의 근거가 필요한가? | 예 — 팩트체크 특성상 근거 원문 제시가 핵심 기능이다 |
| 잘못된 답변을 줄여야 하는가? | 예 — 투자 관련 정보라 hallucination 리스크가 크고, 규제상 근거 없는 주장은 금지된다 |
| 데이터가 지속적으로 변경되는가? | 예 — 신규 공시가 매일 발생한다 |
| 사용자가 원문을 확인할 필요가 있는가? | 예 — 최종 판단은 항상 사용자 몫이므로 원문 링크가 필수다 |

### 6.2 RAG가 필요한 이유

| 항목 | 작성 내용 |
| --- | --- |
| RAG가 필요한 핵심 이유 | 최신·방대한 공시 원문에서 정확한 근거를 검색해 사실 여부를 판단해야 하므로, 사전학습 지식만으로는 불가능하다 |
| 일반 LLM 대비 이점 | 최신 공시를 반영하고, hallucination 대신 실제 원문 근거를 제시한다 |
| 단순 키워드 검색 대비 이점 | 유사 표현(화법)을 클러스터링하고, 자연어 루머 문장에서 종목·키워드를 자동 추출한다 |

### 6.3 프로젝트에서 RAG가 담당하는 역할

사용자 입력(루머/공시 문장) → 종목·키워드 자동 추출 → DART 공시 하이브리드 검색 →
근거 문장 선별(claim verification) → 사실 나열 + 화법 통계 결합 답변 생성 → 근거 공시
원문 링크 제공

### 7.1 검색이 어려울 것으로 예상되는 부분

| 항목 | 작성 내용 |
| --- | --- |
| 표·이미지/OCR 이슈 | 재무제표는 표 형태가 많아 텍스트 추출 시 구조 손실 우려 |
| 긴 문서 또는 복잡한 문서 구조 | 사업보고서는 매우 길고 목차 구조가 복잡함 |
| 유사·중복 문서 | 정정공시가 원공시와 유사한 내용을 반복함 |
| 제품명·코드·고유명사 등 정확한 키워드 검색 필요 | 종목명 약칭/한글-영문 혼용, 테마 키워드(초전도체 등)의 정확한 매칭이 필요 |

| 다국어 혼합 | 일부 공시에 영문이 병기됨 |
| 가장 큰 검색 난점 | 공시 서식별로 구조가 상이해 통일된 청킹 규칙을 세우기 어려움 |

| 설계 영역 | 검토할 방법 | 초기 선택 | 선택 이유 |

| 문서 분할 | Fixed-size / Recursive / Semantic / 구조 기반 | 구조 기반(서식 표준 항목 경계) | 공시서식이 이미 표준 항목으로 구조화돼 있어 그대로 청크 경계로 쓰는 것이 의미 보존에 유리 |
| 검색 | Vector Search / BM25 / Hybrid Search | Hybrid Search | 종목코드·정확 키워드 매칭(BM25)과 의미 유사도(벡터)가 둘 다 필요 |
| Embedding | 사용할 Embedding 모델 | 미정 — Phase 1에서 결정(로컬 한국어 모델 후보 검토 중) | 한국어 금융 텍스트 특화 필요, 비용 절감 |
| 검색 결과 수 | Top-K | K=10 내외(초기값, 튜닝 예정) | 과다 노출 방지와 재현율의 균형 |
| 검색 결과 개선 | Reranking / MMR | 메타데이터 필터 우선, 필요 시 reranking 검토 | 서식유형·날짜 필터만으로 상당 부분 정확도 확보 가능할 것으로 예상 |
| 질문 개선 | Query Rewrite / Multi Query | Query Rewrite(자연어 루머 → 종목명/키워드 구조화 추출) | 비정형 루머 문장에서 검색 가능한 쿼리로 변환 필요 |
| 메타데이터 | 유형 / 날짜 / 카테고리 필터 | 종목코드, 공시일자, 서식유형 | 하이브리드 검색의 정확도를 좌우하는 핵심 필터 |
| 답변 생성 | LLM + Prompt + Citation | LLM + Prompt(사실 나열 강제, 등급·추천 문구 금지) + Citation | 규제 방어선(자본시장법 유사투자자문업 회피)을 프롬프트 레벨에서도 강제 |

## 9. 평가 계획

### 9.1 평가 데이터셋

**초기 평가 질문 수**
20~30건 (과거 실제 테마주 루머 사례 기반 gold set)

**질문 선정 기준**
실제 커뮤니티·뉴스에서 확인된 과거 테마주 루머 사례 중, 사후 공시로 진위가 명확히
판명된 것을 우선 선정한다.
