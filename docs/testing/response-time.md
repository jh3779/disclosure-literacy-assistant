  (main 기준 `_render_meaning_map()`, 레트로 UI에서는 `_build_meaning_snapshot()`).
  무거운 호출(`_phrase_index()`·`_cluster_meanings()`)은 두 경로가 같다.
- **브라우저 렌더링 시간은 빠져 있다.**

## 병목이었던 `_cluster_meanings()` — 2026-09-25 디스크 캐시로 해소 (PR #121)

위 표를 잰 시점에는 이 함수만 디스크 캐시가 없어 **서버를 켤 때마다 약 4분 20초**가
다시 들었다(②열 295.1초 중 262.4초). 함수 docstring도 "수십 초라 무시할 수준이라
디스크 캐싱은 하지 않는다"고 적고 있어 **판단 근거가 실측과 어긋난 상태**였다.
느려진 원인은 2026-09-22에 문장 추출 정규식(`dictionary/candidates.py`)이 늘어난
영향으로 **추정**하며 프로파일링은 하지 않았다 — 캐시는 원인과 무관하게 재기동
비용만 없앤다.

**캐시 적용 후 실측**(같은 코퍼스 82,876섹션·클러스터 3,658개, macOS):

| | 시간 |
| --- | ---: |
| 캐시가 없을 때 계산 | 123.9초 |
| **재기동 후(디스크 캐시 적중)** | **2.6초** |

결과는 캐시 적중 시 원본과 동일함을 확인했다. 첫 계산이 위 표의 257.5초·262.4초보다
짧은 것은 **측정 기기가 달라서**다(위 표는 Windows PC, 이 측정은 macOS) — 절감 방향은
양쪽 모두 같다.

**Windows PC 재측정**(위 표와 같은 기기, main `581334e`, 2026-09-25) — 데모 조회 경로

  로드 등이다 — 위 "30초 안쪽" 추정이 이 기기에서 확인됐다.

## 발표 운영 메모

- **재기동 후 첫 조회는 27.1초로 줄었다**(Windows PC 재측정, 위 절). 디스크 캐시
  (`data/cache/`)가 이미 채워진 PC라면 서버를 재시작해도 첫 조회가 30초 안쪽이다.
- **발표 PC가 이 측정 기기와 다르면 한 번 실제로 재보는 것을 권한다.** 기기·네트워크에
  따라 LLM 대기 시간이 달라진다.
- 안전책은 그대로다 — **발표 전에 서버를 미리 띄우고 아무 조회나 한 번 해 두면**
  이후 조회는 3~5초다. 캐시가 아직 비어 있는 첫 실행에서는 계산이 한 번 필요하다.
