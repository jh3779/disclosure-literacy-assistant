## 1-1. RAG가 없으면 안 됐던 것 → RAG로 가능해진 것 (2026-09-24 강사 지침 반영)

**LLM 단독(RAG 없음)으로는 이 과제가 성립하지 않는다** — DART 공시는 회사·날짜별로 극도로
구체적인 최신 텍스트라, LLM이 학습 때 외웠을 리가 없다. "이용진 대표이사가 지분을 매도했는가"
같은 질문을 LLM에게 그냥 물으면 근거 문서 없이 그럴듯한 답을 지어낼 수밖에 없고(hallucination),
이 프로젝트가 절대 허용할 수 없는 상황이다 — "공시에 실제로 뭐라고 쓰여 있는가"만 다루겠다는
규제 방어선(1절) 자체가 실제 문서를 먼저 찾아온다는 전제 없이는 지켜질 수 없다.

| | RAG 없이(LLM 단독) | RAG로(이 시스템) |
| --- | --- | --- |
| L2a 팩트체크 | 학습 데이터에 없는 최신·개별 공시 내용을 물어보면 그럴듯한 답을 지어낼 수밖에 없다 | L0(수집)이 모은 실제 DART 공시를 L1(검색, `retrieval/company_index.py`)이 클레임과 관련된 섹션만 찾아오고, LLM은 "목록에 없는 내용을 지어내면 안 된다"는 프롬프트 제약(`factcheck/verify.py`의 `_EXTRACT_SYSTEM_PROMPT`) 아래 그 섹션 안에서만 사실을 뽑는다 |
| 근거 제시 | 답변에 실제 출처가 없어 "진짜 공시에 있는 말인지" 검증 자체가 불가능 | 2차 LLM 호출로 뽑힌 사실이 진짜 검색된 문서 안에 있는지 재검증하는 groundedness guard(`verify.py`)를 거치고, 통과한 사실마다 DART 원문 링크가 그대로 붙는다(`_dart_source_url`) — 근거 없는 사실은 버려진다 |
| L2b 화법통계 | "이 상투구 뒤에 과거 몇 건 중 몇 건이 X로 이어졌는가" 같은 통계는 LLM이 자기 지식만으로 답할 수 있는 종류의 질문이 아니다 | 실제 코퍼스(공시 11,081건 라벨링, A 담당)를 검색·클러스터링·집계해야만 나오는 수치이고, 이 집계 자체가 검색(RAG의 R) 없이는 애초에 성립하지 않는다 — 실측치: 클러스터 3,953개, 사후 이벤트 라벨 60,391건(5-2절) |

**정직하게 남겨야 할 지점**: RAG + 2단 방어선(관련성 판단 프롬프트 + groundedness guard)을
쓰고도 hallucination이 19.2% 남았다(5-1절 실측, 5회 평균). 이 수치는 "RAG를 썼는데도 남은 값"이라는
맥락으로 제시해야 한다 — RAG 없이 LLM 단독이었다면 이 정도조차 측정·통제 자체가 불가능했을
거라는 대비가 핵심 메시지다.

### 5-2. L2b 화법통계 (`eval/l2b_holdout.py` + 클러스터 통계)

현재 코드(PR #104 후보 풀 재설계 반영) 기준 실측 — 클러스터 3,953개, 사후 이벤트 라벨
60,391건, 회사 100개:

| 지표 | 실측 | DESIGN.md 목표 |
| --- | ---: | --- |
| 표본(회사 수) 20건 이상 클러스터 | **318개** | 15개 이상 — **달성** |
| 학습 절반에서 FDR 보정 통과한 (클러스터, 사후이벤트) 조합 | 125개 | — |
| **held-out 재현율**(검증 절반에서도 유의) | **4.0%** (125개 → 5개) | — |

**이 두 줄이 모순처럼 보이지만 사실 이 프로젝트의 핵심 스토리다**: 표본은 목표를 훨씬
넘겨 모았는데, split-half held-out 재검증을 통과하는 "예측 신호"는 4%뿐이다. 통과한 125개
중 상당수가 표본 1~3개짜리 클러스터라(예: `train 1/1`, `1/2`) 기저율 대비 z값만 높게
나온 것이고, 검증 절반에서는 그대로 무너진다 — held-out 검증이 정확히 제 역할을 한 셈이다.

그래서 L2b를 **예측형에서 서술형으로 재설계**했다(PR #90 — "이 표현 뒤에 X가 일어난다"가
아니라 "이 표현은 주로 어떤 공시 유형에 나타난다"). 데이터가 뒷받침하지 않는 주장을 접은
결정이고, 이제 그 결정에 재현 가능한 근거가 붙었다.

> **재현 방법**
>
> ```bash
> uv run python -m disclosure_lit.eval.run_eval      # L2a 팩트체크
> uv run python -m disclosure_lit.eval.l2b_holdout   # L2b held-out
> ```
>
> 주의 1: L2b는 캐시가 없으면 사후 이벤트 라벨을 새로 계산하느라 20~40분 걸린다(한 번
> 계산하면 디스크 캐시에 저장돼 이후엔 즉시 끝난다).
> 주의 2: **위 4.0%는 PR #111(이슈 #110) 병합 이후의 코드에서만 재현된다.** 병합 전
> 코드로 같은 데이터를 세 번 돌리면 1.5% / 9.1% / 40.1%로 제각각 나왔다(실측).
> 2026-09-22 병합 완료됐으므로 현재 main에서는 그대로 재현된다.

## 6. 기술적 하이라이트 (심사 어필 포인트)

- **통계적 엄밀성 3단계**: 결정적 클러스터링(PR #89) → FDR 다중비교 보정(PR #89) →
  split-half held-out 재검증(`eval/l2b_holdout.py`, 재클러스터링 없이 라벨만 분할해 비결정성
  문제 우회).
- **우측 절단(right-censoring) 처리**: 사후 이벤트 라벨링에서 "관찰 기간이 아직 안 끝난
  최근 공시"와 "이벤트가 실제로 없었던 공시"를 구분(PR #56) — 안 하면 최근 데이터가 전부
  "이벤트 없음"으로 왜곡됨.
- **성능 개선**: 콜드스타트 40분→2분(PR #91, 디스크 캐싱), sections.jsonl 재작성
  O(n²)→O(n)(PR #69), FAISS 벡터 검색 도입(PR #86).
- **안정성**: 네트워크 오류 격리(PR #68), corp_code 캐시 TTL 경고(PR #70), 공시 서명란 제거로
  hallucination 오탐 방지(PR #71).

   커서 그 방어선이 다단어 검색에서 재발할 수 있던 문제) — 전부 수정.
4. **"숨은 오류·충돌로 인한 멈춤"이라는 다른 시각으로 `main` 자체를 감사**: 로직 정확성이
   아니라 크래시·행(hang)·경쟁 상태 관점으로 재검토해 HIGH 2건을 새로 발견 — LLM API
   호출에 타임아웃이 없어 최악의 경우 최대 10분 멈출 수 있던 문제(SDK 기본값 직접 확인),
   두 사용자가 거의 동시에 같은 종목을 조회하면 데이터가 중복 인덱싱될 수 있던 경쟁 상태
   (스레드 시뮬레이션으로 5/5 재현). 반대로 "테스트에서 발견된 라이브러리 충돌이 실제
   서비스에도 있는가"라는 가설은 직접 재현을 시도해 **기각**(프로덕션 코드가 문제의
   모듈을 애초에 안 씀을 grep으로 확인) — 있어 보이는 문제를 있다고 우기지 않고 검증해서
   가려낸 사례.
5. **비용 대비 효과 판단도 근거로 남김**: 클러스터링 알고리즘이 이론적으로 O(N²) 특성을
   갖는다는 걸 실측(N 2배→시간 약 4배)으로 확인했지만, 실측 결과 이게 전체 콜드스타트의
   21%(약 30초, 일회성 캐시 비용)에 불과하고 알고리즘 교체 비용(재검증 범위)이 이득보다
   크다고 판단해 "지금은 고치지 않는다"는 결정을 근거와 함께 기록 — 무조건 고치기보다
   트레이드오프를 재는 과정 자체를 보여줄 수 있는 지점.

- **"전환사채" 예시 문장은 후보 6개사 전부에서 결과가 빈약했다.** 녹화에는 유상증자 문장을 쓴다.
- **골드셋 종목(삼성전자·SK하이닉스 등 14개사)은 데모에서 고를 수 없다** — 공시 데이터는
  `data/raw`에 있어 평가는 정상적으로 돌지만, 드롭다운 목록(`corpus_companies.json`,
  100개사)에 그 14개사가 빠져 있다. 발표에서 평가 사례와 데모 사례가 다른 이유가 이것이다.
- **편집 메모**: ① 근거 원문은 한 번 펼쳐 보여주고 바로 접는다(길게 스크롤하면 빽빽한 법률
  문장이 화면을 채운다) ② 같은 사실이 여러 공시에서 반복돼 같은 문장이 여러 줄 나오는
  구간은 잘라낸다 ③ 탭 전환 직후 1~2초는 목록이 그려지기 전이라 비어 보인다 — 그 공백도
  잘라낸다(기능 문제가 아니다).

### 녹화 시 참고

- **촬영 중 사고 방지**: 결과를 띄워둔 뒤 예시 칩이나 종목을 바꿔도 결과가 사라지지 않고,
  LLM 타임아웃이 나도 스택트레이스 대신 안내 문구가 뜬다(DEC-038·DEC-039) — 재촬영 부담이
  줄었다.
- **레트로 연출은 입장·입력 영역에 한정**되고 결과·사전·조회 기록은 밝은 화면이다 —
  영상에서 톤이 한 번 바뀌는 지점이라 컷 전환으로 활용하면 자연스럽다.

  않는다(`docs/03_screen_contract.md` "시각·접근성 계약") — 규제 방어선을 영상에서도
  일관되게 보여준다.

## 9. 예상 Q&A 대비

- **"왜 등급/추천을 안 주나요?"** → 자본시장법 유사투자자문업 회피가 설계 최우선 제약(1절).
- **"정확도는 얼마나 되나요?"** → 5-1절 실측치로 답한다: **골드셋 25건·5회 반복 기준 평균
  재현율 76.3%(74.0~80.3%), hallucination 19.2%(16.0~22.0%)**(gpt-4o-mini). 목표(80%)에는
  3.7%p 못 미쳤다는 걸 먼저 인정하고, 회차마다 16~18건은 재현율 100%로 양극화돼 있다는
  분포를 덧붙이는 게 정확하다. "왜 80%를 못 넘었나"를 물으면 5회 모두 0%였던 3건이
  어떤 유형인지(검색이 근거 공시를 아예 못 찾은 케이스)로 답할 수 있다. "한 번 잰 값이냐"는
  질문에는 5회 반복해 범위까지 쟀다는 게 그대로 답이 된다.
- **"지어낸 답(hallucination)은 어떻게 막나요?"** → 2단 방어선(추출 프롬프트의 관련성
  기준 + groundedness guard 2차 LLM 검증)을 설명하되, **실측 19.2%가 남았고 4건은 5회 모두 100%였다**는
  걸 숨기지 않는 게 낫다. 금융 도메인에서 "0%로 막았다"는 주장은 검증 질문을 부를 뿐이고,
  이 프로젝트는 오히려 "측정해서 알고 있다"가 강점이다.
- **"경쟁 서비스와 뭐가 다른가요?"** → 1절 차별점 참고, "직접 경쟁 서비스 미발견"은 재검증
  권장 문구가 원문에 있으므로 과신해서 단정하지 말 것.
- **"화법통계가 결국 예측 아닌가요?"** → PR #90에서 "예측형"에서 "서술형 3기능(흔함도·
  자기상관·회사별 흐름)"으로 재설계한 이유를 설명 — 과거 통계 서술이지 미래 예측이 아니라는
  점을 명확히.
- **(신규) "AI가 코드를 다 짰다면서 왜 이렇게 버그가 많이 나왔나요?"** → 관점을 뒤집어 답할
  것: 버그 자체보다 "그걸 병합 전에, 여러 독립 시각(외부 리뷰·재검증·전체 diff 감사·런타임
  견고성 감사)으로 겹겹이 걸러내는 프로세스를 실제로 운영했다"는 게 핵심 메시지(6절 신규
  항목). 사람이 짠 코드도 리뷰 없이는 같은 비율로 결함이 나온다 — 오히려 이 정도 밀도의
  교차검증은 소규모 팀에서 사람 리뷰만으로는 현실적으로 어렵다.
- **"리뷰 승인 없이 병합한 PR이 있던데요?"**(2026-09-25 갱신 — 이제 열린 PR은 0건이다)
  → 사실대로 답한다. #113·#114·#115는 팀 리뷰를 받고 지적을 반영했지만, **#115는 재리뷰
  전에, #117~#123은 승인 0건 상태에서 관리자 권한으로 병합**했다(발표 일정 때문). 대신
  CI·테스트·별도 워크트리 독립 재현으로 검증을 대체했다는 점을 덧붙인다. 규칙을 지켰다고
  포장하지 말 것 — 지키지 못한 이유와 대체 수단을 말하는 쪽이 신뢰가 간다.
- **"조회 기록은 어디에 저장되나요?"** → 앱 프로세스 메모리에 최근 30건. DB는 쓰지 않았고,
  서버를 재시작하거나 캐시를 지우면 사라진다. 과제 범위에서 영속 저장은 목표가 아니었다.
- **"기록을 다시 열면 LLM을 또 부르나요?"** → 아니다. **조회 당시 결과를 스냅샷으로
  저장**해 재열람 시 LLM·임베딩 재호출이 없다. 이 동작은 테스트로 고정돼 있다(재조회가
  일어나면 실패하도록 감시).
- **"여러 사람이 같이 쓰면 기록이 섞이지 않나요?"** → 섞인다. 같은 서버에 접속하면 기록을
  **공유**하고 계정별 분리는 하지 않았다(시연·사내 도구 전제). 실서비스로 가면 분리가
  필요하다 — 이건 한계로 인정하는 게 맞다. 데모 영상에도 이전 조회가 함께 보인다.
- **"응답이 느리지 않나요?"** → 준비된 상태에서 **3~5초**로 목표(10초)를 충족한다. 서버를
  새로 띄운 직후 첫 조회만 27초인데, 이건 측정해서 병목(`_cluster_meanings()`)을 찾아
  디스크 캐시로 **295초 → 27초**로 줄인 결과다(5-3절). "재보고 고쳤다"는 과정으로 답한다.

## 10. 발표 후 피드백과 대응 계획 (2026-09-30 추가)

발표 후 받은 피드백 5가지를 그대로 옮기고, 각 항목에 대해 **지금 가진 근거**와 **비어 있는
것**을 구분해 적는다. PPT를 수정할 때 이 표를 출발점으로 쓴다.

### 받은 피드백과 현재 위치

| 피드백 | 지금 가진 근거 | 비어 있는 것 |
| --- | --- | --- |
| 성능 개선 | 응답시간 295초 → 27초(병목 측정 → 디스크 캐시) | **품질 지표는 개선 이력이 없다** — 76.3%는 한 번 잰 값 |
| 문제 정의 잘 하기 | 확인 비용 문제를 구체적으로 서술 | **사용자 검증 없음** — "쓸 것이다"는 가정 |
| 문제 해결력 강조 | 가설 반증 후 기능 축소, 필터 경계 실측, 순환 의존 제거 | 사례는 강한데 **하나의 서사로 안 엮임** |
| 점진적 발전 | 성능 쪽만 before/after 존재 | **품질 쪽 before/after 표가 없다** |
| 사용자 관점 해결 범위 | 확인 비용↓, 해석은 사용자 몫 | **실패했을 때 실패라고 말하지 않는다** |

마지막 줄이 핵심이다. 지금은 근거를 못 찾아도 답을 만들어낸다 — 사용자는 "찾지 못했다"를
받아야 할 상황에 **지어낸 사실**을 받는다.

### 해결 범위를 3단으로 말한다

| 단계 | 해결 여부 |
| --- | --- |
| **찾기** — 어느 공시에 그 내용이 있는지 | ✅ 해결 |
| **읽기** — 관련 사실만 추려 원문 근거와 함께 제시 | 🟡 부분 해결 |
| **해석·판단** — 그래서 사고팔지 | ❌ **의도적으로 미해결** |

세 번째는 "못 한 것"이 아니라 **"안 하기로 한 것"**이다. 여기에 더해 **검색이 실패한
케이스(25건 중 3건)에서는 도움이 되지 않는다**는 사실도 같이 말하는 게 정확하다.

### 문제 정의 문장 다듬기

- ❌ "관련 문서 내용을 **정확히 판단**하기 어렵다" → 듣는 사람은 "판단을 도와주는군요"로
  받는다. 우리 해결책과 어긋난다.
- ✅ "공시에 **무엇이 적혀 있는지 확인하는 비용**이 초보자에게 지나치게 크다"

대상을 "주식을 막 시작한 사람·대학생"으로 좁힌 것은 유지한다 — 청중이 사람을 그릴 수 있다.

### 개선 로드맵 (품질 쪽 before/after 만들기)

| 단계 | 내용 | 측정 가설 |
| --- | --- | --- |
| v1 (현재) | 기준선 | 재현율 76.3% / 환각 19.2% |
| v2 | **기권 설계** — 근거를 못 찾으면 답하지 않고 "찾지 못했다"고 말한다 | 환각률 하락, 재현율은 거의 유지(0%였던 케이스는 원래 못 찾던 것) |
| v3 | **검색 개선** — 5회 모두 0%였던 3건의 실패 원인 분석 후 반영 | 재현율 상승 |

각 단계마다 **5회 반복 측정**해 아래 표를 채운다. 이 표 하나가 "점진적 성능 발전"에 대한
답이 된다.

| 버전 | 재현율 | 환각률 | 기권율 | 변경 내용 |
| --- | --- | --- | --- | --- |
| v1 | 76.3% | 19.2% | 0% | 기준선 |
| v2 | ? | ? | ? | 기권 설계 |
| v3 | ? | ? | ? | 검색 개선 |

기권 설계를 먼저 두는 이유는 **성능·사용자 관점·문제 해결력 세 항목을 한 조치로 채우기**
때문이다.

### 루머 분류를 추가한다면

- ❌ **진위 분류**(사실/거짓/미확인)는 하지 않는다. "종합 판정을 만들지 않는다"는 원칙을
  정면으로 깨고, 재현율 76%·환각 19%로 "이 루머는 거짓"을 출력하면 다섯 번에 한 번은
  근거 없이 거짓 판정을 내리게 된다.
- ✅ **사안 유형 분류**(유상증자/전환사채/M&A/신사업)는 판단이 아니라 라우팅이며,
  유형별 공시 서식으로 검색 범위를 좁혀 **검색 품질을 올릴 수 있다**.
- ✅ **검증 가능성 분류**("이 루머가 공시로 확인 가능한 종류인가")는 데이터 가용성에 대한
  진술이라 안전하고, **기권 설계와 바로 이어진다**. "커뮤니티 루머 중 공시로 확인 가능한
  비율"은 그 자체로 문제 정의의 경계를 보여주는 데이터가 된다.

### 최신성 — 2026-09-30 일부 반영됨 (PR #127)

근거의 시점을 사실 그대로 노출했다. **평가 표현은 쓰지 않는다** — "오래된 루머입니다"는
무시해도 된다는 판단으로, "최신 정보입니다"는 신뢰도 보증으로 읽힌다.

- 사실 목록을 접수일 최신순으로 정렬
- **가장 최근 근거 날짜와 코퍼스 수집 종료일을 병기** — 근거 날짜만 보여주면 "그 뒤로
  아무 일도 없었다"는 착시가 생긴다(실제로는 배치 수집이 거기서 끝났을 뿐)
- 재공시 예정 건수 요약 + 각 사실 아래 일정 표시

남은 것: 루머 시점과 공시 시점의 **선후 관계**(루머 이후 나온 해명 공시인지)는 사용자가
루머 시점을 입력해야 해서 보류했다.
